# راهنمای برچسب‌زنی انسانی (دو ارزیاب مستقل)

## هدف
برای هر جفت فایل قبل/بعد گردش‌کار GitHub Actions بگویید آیا تغییر یک **پسرفت امنیتی** است یا نه.

## قانون طلایی
- **فقط** محتوای `before_path` و `after_path` را بخوانید.
- به خروجی اعتبارسنج، `gold_has_regression`، یا پیش‌بینی zizmor نگاه **نکنید**.
- فایل `predicate_gold_key.csv` فقط برای تحلیل‌گر است؛ ارزیاب‌ها نباید آن را باز کنند.

## تعریف پسرفت
برچسب `has_regression = 1` اگر و فقط اگر وضعیت امنیتی بعد نسبت به قبل **بدتر** شده باشد، مثلاً:
- مجوز گسترده‌تر (`write-all` یا scopeهای خطرناک مثل `contents: write` / `id-token: write`)
- تریگر خطرناک جدید (`pull_request_target`, `workflow_run`, `issue_comment`, …)
- از دست رفتن پین SHA روی اکشن موجود
- اکشن شخص‌ثالث جدید بدون پین (صاحبان خیلی رایج مثل `actions/` معمولاً برای این مورد نرم‌تر دیده می‌شوند)
- الگوی لو رفتن secret یا تزریق `github.event` / نوشتن به `GITHUB_ENV`
- `curl|bash` یا مشابه
- حذف کنترل امنیتی (CodeQL و …)
- افزودن `self-hosted`

برچسب `0` اگر:
- فقط سخت‌سازی باشد (پین کردن، افزودن CodeQL)
- ناامنی از قبل بوده و عوض نشده
- تغییر بی‌ربط به امنیت باشد

## ستون‌ها در CSV
| ستون | مقدار |
|------|--------|
| `has_regression` | `0` یا `1` (اجباری) |
| `rule_ids_optional` | مثلاً `R05\|R12` اختیاری |
| `confidence` | `low` / `med` / `high` |
| `notes` | توضیح کوتاه فارسی/انگلیسی |

## فرایند (تحویل فعلی: تک‌ارزیاب)
1. ارزیاب A فایل `annotator_A.csv` را پر می‌کند.
2. ارزیاب دوم در محدودهٔ این تحویل نیست؛ `annotator_B.csv` لازم نیست.
3. از ردیف‌های پرشدهٔ A طلای انسانی ساخته می‌شود → `gold_human_adjudicated.csv`.
4. اجرا: `python scripts/eval_human_gold.py`
